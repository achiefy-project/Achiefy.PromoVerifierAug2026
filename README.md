# Проверка розыгрыша Achiefy

Этот репозиторий существует ради одного: **любой человек может сам пересчитать победителей
розыгрыша и убедиться, что организатор ничего не подкрутил.** Не нужно верить нам на слово и не
нужно ничего запрашивать — всё считается по двум публичным файлам.

Здесь лежит скрипт `verify.py` (чистый Python, без библиотек) и описание алгоритма. Проверка
занимает минуту.

---

## Как это возможно

Розыгрыш устроен так, что у организатора нет момента, в который он мог бы повлиять на результат:

1. **Список участников замораживается** в момент окончания акции и публикуется файлом
   `snapshot.json`: кто участвует и сколько у кого билетов. После публикации он не меняется.
2. **Источник случайности — Bitcoin**. Заранее, ещё до окончания акции, объявляется момент времени.
   Победителей определяет hash первого Bitcoin-блока, появившегося после этого момента. В момент
   публикации snapshot'а этого блока ещё не существует — ни у кого, включая организатора, нет
   способа его предсказать или заказать.
3. **Расчёт полностью детерминирован**: из hash'а блока получается число, число указывает на
   выигрышный билет. Одни и те же входные данные всегда дают одних и тех же победителей — этот
   скрипт это и проверяет.

Иначе говоря: состав зафиксирован **до** появления случайности, а случайность никто не контролирует.

---

## Что нужно

* **Python 3.8 или новее.** Проверить: `python --version` (на некоторых системах — `python3`).
  Скачать: <https://www.python.org/downloads/>. Больше ничего устанавливать не нужно —
  скрипт использует только стандартную библиотеку.
* Два файла с сайта кампании: `snapshot.json` и `result.json`. Ссылки на них публикуются в
  итоговом посте.

## Проверка за три шага

**1. Скачайте этот репозиторий** (кнопка «Code» → «Download ZIP», либо `git clone`).

**2. Скачайте файлы кампании** — ссылки берите из итогового поста в канале:

```bash
curl -o snapshot.json https://<домен-кампании>/promo/snapshot.json
curl -o result.json   https://<домен-кампании>/promo/result.json
```

Можно и просто открыть эти адреса в браузере и сохранить страницы как файлы
(«Сохранить как…», тип «Все файлы», имена `snapshot.json` и `result.json`).

**3. Запустите проверку:**

```bash
python verify.py --snapshot snapshot.json --result result.json
```

Хотите проверить ещё и то, что взят правильный блок Bitcoin (нужен интернет):

```bash
python verify.py --snapshot snapshot.json --result result.json --online
```

Последняя строка вывода — вердикт. `РЕЗУЛЬТАТ: всё сошлось` означает, что победители в точности
такие, какими их обязан был дать опубликованный алгоритм.

Убедиться, что сам скрипт считает правильно, можно без файлов кампании:

```bash
python verify.py --self-test
```

Самопроверка прогоняет контрольные векторы, которые зафиксированы и в коде розыгрыша, — если
они сошлись, обе реализации считают одинаково.

## Что именно проверяет скрипт

| Проверка | Что доказывает |
| --- | --- |
| SHA-256 файла `snapshot.json` совпадает с записанным в `result.json` | список участников не подменили после розыгрыша |
| ID участников уникальны, сумма билетов сходится | таблица билетов не «дорисована» |
| Состав каждого раунда зафиксирован раньше момента его случайности | исключения нельзя подобрать под уже известный блок |
| Переролл объявлен публично до момента случайности | о пересмотре результата узнали заранее, а не задним числом |
| `--online`: блок с такой высотой существует и его hash совпадает | результат привязан к реальной цепочке Bitcoin |
| `--online`: блок появился **после** объявленного момента, а более ранних подходящих блоков нет | взят именно первый подходящий блок, а не удобный |
| Пересчёт всех раундов даёт ровно объявленных победителей | никто не заменил победителя вручную |

## Как работает алгоритм

### Билеты

Билеты начисляются за задания кампании (регистрация, подписка, полезное действие, опрос) по
опубликованной таблице; максимум — 10 билетов на участника. Итоговое количество у каждого участника
уже посчитано и зафиксировано в `snapshot.json` — скрипт берёт числа оттуда и ничего не
пересчитывает по заданиям.

В файле участник выглядит так (личных данных нет — только анонимный ID):

```json
{ "publicId": "38aa3a93c1f04e6b8a2d5c7e9f0a1b2c", "registered": true, "subscribed": true,
  "usefulAction": true, "surveyCompleted": false, "tickets": 7 }
```

Свой полный `publicId` каждый участник видит в боте и может найти себя в списке.

### Случайность

Берётся **блок с наименьшей высотой, чей timestamp ≥ объявленного момента**. Отметки времени у
блоков не строго возрастают, поэтому «первый» считается по высоте, а не по порядку появления, и блок
должен получить как минимум 3 подтверждения. Организатор дополнительно сверяет блок по двум
независимым обозревателям; вы можете сверить его по любому третьему.

### Выбор победителя

Для каждого разыгрываемого места `p`:

```text
1. Берём участников с tickets > 0, кроме исключённых, и сортируем по publicId
   по возрастанию (обычное сравнение строк).
2. remaining = сумма их билетов.
3. r = SHA256( blockHash_в_нижнем_регистре + ":" + p ), прочитанный как одно
   большое беззнаковое целое число (big-endian), взятый по модулю remaining.
4. Выкладываем билеты участников в одну линию в порядке сортировки и идём по ней,
   накапливая сумму. Победитель — тот, на чьём отрезке оказалось число r.
5. Победитель выбывает из розыгрыша следующих мест: один участник — один приз.
```

Пример на пальцах. Участники `aaaa` (7 билетов), `bbbb` (5), `cccc` (9), всего 21 билет.
Линия билетов: места 0–6 принадлежат `aaaa`, 7–11 — `bbbb`, 12–20 — `cccc`. Если для первого места
`r = 9`, выигрывает `bbbb`.

Так как SHA-256 нельзя обратить, а hash блока становится известен только после фиксации списка,
подобрать «нужного» победителя невозможно — можно лишь честно посчитать.

### Перерроллы

Если после розыгрыша среди победителей находят явные боты (фермы мультиаккаунтов, накрутка), их
места переигрываются. Правила жёсткие и проверяемые:

* организатор **сначала публикует** список исключённых ID с причинами и новый момент случайности —
  и только потом появляется блок, который решает исход;
* переигрываются **только освободившиеся места**; остальные победители сохраняют призы и в новом
  розыгрыше не участвуют;
* исключённые участники не возвращаются в последующие раунды;
* каждый раунд со своим блоком, своими исключениями и своими местами попадает в `result.json`;
* поле `"status"` показывает, окончательный ли результат (`approved`) или ещё может быть
  пересмотрен (`provisional`).

Скрипт проигрывает раунды по порядку: раунд 1 даёт исходных победителей, каждый следующий
переигрывает свои места с новым блоком и расширенным списком исключений. Итог обязан совпасть с
объявленным. Если организатор «переиграл» место, не исключив публично его владельца, или объявил
исключения после появления блока — проверка это покажет.

  [ok]   ID участников уникальны (25 шт.)
  [ok]   сумма билетов сходится: 151

Честность раундов
  [ok]   раунд 1: состав зафиксирован до момента случайности
  [ok]   раунд 2: состав зафиксирован до момента случайности
  [ok]   раунд 2: объявлен до момента случайности

Пересчёт победителей

Место | Приз                       | Победитель | Совпадает
------+----------------------------+------------+----------
    1 | $100                       | 38aa3a93…  | да
    2 | $60                        | f6007b17…  | да
    3 | $40                        | 32c0c5bf…  | да
   ...
   18 | Ключ Steam ($1.5)          | fb71aad4…  | да

  [ok]   все 18 мест совпали с опубликованными
РЕЗУЛЬТАТ: всё сошлось. Розыгрыш проведён по опубликованным правилам.

Место 2 здесь занимает `f6007b17…`, а не тот, кто выиграл его в первом раунде: исходный победитель
исключён как бот-аккаунт, и место переиграно на новом блоке. Оба раунда видны в `result.json`.

Если что-то не сходится, скрипт печатает конкретное расхождение (например: «место 2: объявлен X,
пересчёт даёт Y») и завершается с кодом 1.

## Частые вопросы

**А вдруг организатор подменил snapshot после розыгрыша?**
`result.json` содержит SHA-256 файла snapshot'а, а сам snapshot публикуется сразу после закрытия
акции — до появления блока. Подмена ломает хеш, и скрипт это покажет. Пересчёт по «правильному»
snapshot'у даст других победителей, чем объявленные.

**А вдруг он ждал удобный блок?**
Момент случайности объявляется заранее и записан в файлах, а правило — «первый блок после этого
момента». С ключом `--online` скрипт проверяет и это: что у блока подходящий timestamp и что среди
предыдущих блоков нет более раннего подходящего.

**А вдруг он дописал себе билетов?**
Список билетов публикуется в snapshot'е до розыгрыша, и всю кампанию виден в живой таблице
участников. Любой участник видит там себя и может убедиться, что таблица не изменилась.

**Почему в списке анонимные ID, а не имена?**
Чтобы участие в розыгрыше не раскрывало ничего о человеке. `publicId` — случайный идентификатор,
он не связан с профилем и не говорит ни о личности, ни об аккаунте. Свой ID участник видит в боте.

**Я не нашёл себя в списке.**
Значит, на момент окончания акции регистрация в боте не была завершена. Спорные случаи — в
поддержку кампании; сам розыгрыш от этого не зависит, он считается по опубликованному файлу.

**Могу я написать свою проверялку?**
Да, для этого здесь и описан алгоритм. Нужны только SHA-256, целочисленная арифметика и сортировка
строк — реализуется на любом языке за пару десятков строк. Если ваш результат разошёлся с нашим —
напишите нам, это важнее любого приза.

## Файлы репозитория

| Файл | Что это |
| --- | --- |
| `verify.py` | скрипт проверки (стандартная библиотека Python, без зависимостей) |
| `examples/snapshot.json` | пример замороженного списка участников |
| `examples/result.json` | пример результата с раундами и блоками |
| `README.md` | этот файл |

Пример можно прогнать прямо сейчас, до старта кампании:

```bash
python verify.py --snapshot examples/snapshot.json --result examples/result.json
```

Файлы в `examples/` — с тестового прогона: участники сгенерированы, а «блок» синтетический, не из
реальной цепочки Bitcoin. Поэтому запускать пример с `--online` смысла нет: проверка блока
предназначена для настоящих файлов кампании.
